# 1001 Code is a fork of T3 Code

This repository is [pingdotgg/t3code](https://github.com/pingdotgg/t3code) plus 1001's changes. Upstream lands more than a hundred commits a day and we want all of them. Two things make that possible: how upstream gets merged, and how we write our own changes.

## How upstream gets in

[upstream.json](upstream.json) names the upstream commit this fork already contains. `node scripts/sync-upstream.ts` merges everything upstream has added since and moves that pointer. To run a sync, ask an agent to "sync upstream"; it follows the [sync-upstream skill](../.agents/skills/sync-upstream/SKILL.md).

- **Each sync lands as one merge commit.** Its parents are the fork's `main` and the upstream commit it syncs to, so `main` keeps upstream's history and `git blame` and `git bisect` see upstream's own commits. Land a sync pull request with **Create a merge commit**. A squash merge drops that history; the next sync still works, because the pointer records what was merged, but blame and bisect lose upstream's commits.
- **Use the tool, not `git merge upstream/main` or GitHub's "Sync fork".** With upstream's history in `main` a plain merge would apply, but it takes upstream's newest commit, skips the checks below and leaves the pointer behind.
- **Upstream code waits before it comes in.** Without `--to`, a sync targets the newest upstream commit at least three days old (`--min-age-days`) whose `Check` job passed on upstream's CI when it was pushed to upstream's `main`, also at least three days ago. A bad commit gets those days to be noticed upstream before it reaches the fork. If the tool cannot read upstream's CI, it refuses to choose rather than guess; `--to <commit>` names a target someone has checked by hand.
- **Upstream code never runs on a machine with credentials.** Between merge and review, the sync branch holds upstream code nobody here has read. The agent that syncs merges text and resolves conflicts; it does not install, build, test or run repository scripts on that branch. The tool turns git hooks off for its own git commands and refuses an upstream change to its own files. The fork's CI runs the checks on GitHub's runners, which hold no secrets. Anything that has to run before that happens in a disposable environment without credentials.
- **The pull request opens with the sensitive changes.** `finish` lists every upstream-changed file that matches a sensitive rule, grouped by why: dependencies added to the lockfile, install-time build permissions and release age, package scripts and lifecycle hooks, CI workflows, agent instructions, update and release URLs, telemetry, auth and secrets code, Dockerfiles, and setup scripts and git hooks. The rules are in [sensitive-changes.ts](../scripts/lib/sensitive-changes.ts).
- **The tool stops at the one upstream commit that conflicts.** It merges as far as it can without a decision, so every conflict arrives with the pull request that caused it, and a clean day needs no decisions at all.
- **A clean merge is not proof.** Upstream can change what a fork feature stands on without touching the same lines. `status` and the sync report list every upstream commit that touches a file the fork has changed, and the fork's CI runs on every sync.

The newest fetched upstream stays at `refs/sync-upstream/upstream` after any `status` or `merge`, and each sync's step-by-step merges at `refs/sync-upstream/detail/<commit>` in the checkout that ran it.

## How a release gets out

A release is the `stable` tag: team installs build the commit it names and offer it as an update, so moving it ships to everyone. Only the people the tag's ruleset lets bypass can move it. To release or roll back, ask an agent to "release"; it follows the [release-stable skill](../.agents/skills/release-stable/SKILL.md).

## Rules for our changes

A textual conflict costs an agent minutes. A fork change that nobody can explain costs far more, at every sync, forever.

1. **Add, don't edit.** New behavior goes in new files. Where upstream's code has to call it, change as few of upstream's lines as you can.
2. **Leave upstream's code alone around your change.** No reformatting, renaming, reordering or moving code in a file upstream owns. Each of those turns upstream's next edit into a conflict that carries no meaning.
3. **Never add a numbered database migration.** Upstream owns that sequence, and a fork migration that takes the next number stops the server starting once upstream uses it. Fork tables need their own migration lane.
4. **Test what you add.** Upstream's tests do not know about our features. Without a test, a fork feature breaks silently the day upstream changes something under it.
5. **Record every divergence below, in the pull request that makes it.** The entry is what lets an agent, months later, resolve a conflict in your code the way you would have.
6. **Chat text stays plain.** A feature that gives message text a meaning (question cards, Re: lines, proposals) uses a markdown convention that reads normally in the official T3 Code clients and other agent harnesses. Only 1001 Code renders it as controls.

When an agent needs the user to decide something, it asks with a question block that the web and desktop clients render as answer controls. T3 Code teaches every agent the format in its own instructions (see [Question format in the agent instructions](#question-format-in-the-agent-instructions)). A feature that needs agents to behave a certain way goes in those instructions, never in a skill: a skill reaches only agents that choose to load it, in this repository.

- **Where:** `.github/workflows/ci.yml`, every `runs-on:` line. Upstream uses Blacksmith runners, which this repository does not have, so its jobs queued forever. Linux jobs run on `ubuntu-24.04`, the macOS lint on `macos-26`. Both are free for public repositories.

### Only CI workflows are enabled on GitHub

- **Where:** the repository's Actions settings, not a file. Only `CI` and `Agent Context Budget` are enabled; every other upstream workflow is disabled with `gh workflow disable -R 1001-ai/1001-code <name>`.

The question is ordinary markdown, so it reads well in clients without the card, such as the official mobile app, where the user types `Q4: answer`. The card parses the quote's source rather than its rendered tree, so the rules are exact and ordinary quotes stay quotes. Answering sends at once: the card writes `<id>: answer` into the thread's draft and submits through the composer handle in the same tick, setting `promptRef` itself because the composer syncs it from the draft only after a render. Submitting the way the composer's own send button does keeps the user's follow-up behavior (queue or steer), dictation, pending image and context checks, and the typing guard. Anything else in the draft goes with the answer. A single choice sends on click, so its options are a group of buttons, each its own tab stop, rather than radios; a pick-any question toggles options in the draft and sends with its Send button; free text sends on Enter. Every kind has a Skip button at the end of the prompt row (`ghost-muted`, `micro`), which is one more single choice: it answers `<id>: skipped` (`QUESTION_SKIPPED_ANSWER` in `questionCards.ts`, which the agent instructions also read), shows pressed while the draft holds that line, and takes it out on a second click; an answered card reads "Skipped". The agent can withdraw a card itself with a whole `<id>: no longer needed` line outside code blocks in a later reply (`QUESTION_WITHDRAWN_ANSWER` and `questionWithdrawalsInMarkdown` in `questionCards.ts`, so the server reads it the same way). A withdrawn card shows one muted "No longer needed · withdrawn by the agent" line, with no options, Skip or answer controls; an answer still in flight shows as Sending instead. While an approval or a provider's question is open, a send would answer that instead, so the card only writes the draft, as it does without the operate scope, while a queued message is being edited, and wherever there is no composer to send through. When the composer refuses or drops a send (some refusals toast, others do not), the answer stays in the draft, where the card shows it. After a send the composer took, the card shows "Sending" until the answer arrives, so a second click cannot leave a stray line in the draft. The card reads as answered from a later user message, or from a queued one, since a queued message is not a turn item until its run dispatches. Nothing is stored, so there is no server, contract or database change. The wrapper sets the asking item only where the reader can reply (`onReplyToResponse` is set), so the guest page and every other `ChatMarkdown` keep showing the quote. Where cards render, a question id the reply mentions in prose (`(Q40)`) links to the newest card with that id: a remark plugin passed through `ChatMarkdown`'s `extraRemarkPlugins` turns ids into `t3-context://v1/question/<id>` links, its `renderContextReference` renders the ones with a card as a response citation of the card's prompt, and the citation's existing navigation scrolls the virtualized timeline to it and pulses the prompt. No upstream file changes for it, and a streaming message keeps the plain parse.

A voice's `boundary` events set the word; for a voice that sends none, each word's start is estimated from the text (60 ms a character, a pause after a clause) with one timer for each word, and no frame loop. `lampVoiceSpeaker.ts` is the voice the user downloaded and picked (see [Speech output with downloaded voice models](#speech-output-with-downloaded-voice-models)): one `speak` request for each of the layer's sentences, with no voice named, so the one chosen in settings speaks. The PCM plays through one `AudioContext` (`lampAudio.ts`), and each word is set from the returned timings against the audio clock, one timer at a time, with no frame loop. A sentence is asked for when the one before it starts to play, never further ahead, because the server makes one sentence at a time and a cancelled request costs it its worker; audio that is ready before the sentence before it ends is scheduled at that end, so there is no gap when synthesis keeps up. `stop("after-word")` stops at the end the timings give the word in progress, or after 300 ms, then cuts the audio and aborts the request in flight; with no word in progress, as while the first audio is made, it stops at once. `useLampSpeaker` chooses when the layer opens: it reads the voice catalog of the layer's environment (`lampVoiceChoice`), and the downloaded voice speaks only when a voice is picked and its model is installed; a catalog that does not answer in five seconds, or cannot be read, means the system voice. Nothing is said until the catalog has answered. When a request to the downloaded voice fails, or its audio cannot play (the `AudioContext` is not running), the system voice takes over for the rest of that conversation, from the sentence that failed and after the audio already made has played out, and the layer shows one line saying so. With voices on offer and none picked, the header has one control, **Choose a voice**, which closes the layer (the agent would talk on under Settings, over a voice sample) and opens Settings → Voice at `#voice-output`. A text handed to a speaker is `preparing` in the session until the speaker's first report: until then the captions keep the text before it and the status reads Thinking, and a press of Space then records the whole text as not spoken. Nothing is said during the open animation, and a voice speaks only when the open came from a user gesture (`navigator.userActivation`), which speech synthesis and the `AudioContext` both need: the context is opened or resumed in that same commit, and suspended when the layer closes or the system voice is chosen. Without a gesture the text shows as said. The estimated word timings may drift from a real voice, and one text is still one `speak`: between two stretches of an answer the downloaded voice pauses for as long as the next sentence takes to make. **Interrupting:** pressing Space while the agent speaks listens at once, and stops the voice after the word in progress. Where it stopped is kept in the store in `lampVoice.state.ts` as `interruption`: the text spoken, the text not spoken, and the user's transcript once it arrives. Closing the layer stops the voice and cancels a recording. **The agent:** `useLampAgent` calls `voiceAgent.open` when the layer opens (with the draft's `projectId` when the chat is a new one with no thread yet, read from the composer draft store) and `voiceAgent.close` when it closes or unmounts (an open that answers after the layer closed is closed at once), and reads the agent's answer from the hidden voice thread with the ordinary thread detail subscription (`useEnvironmentThread`): the assistant messages created since the conversation opened. `nextLampSpeech` in `lampAgent.logic.ts` hands the voice the answer a few whole sentences at a time: a message that still streams gives only finished sentences, a finished one gives the rest, and markup a model slips in is not read out. Each stretch is one `LampSpeaker.speak`, so the captions show the stretch being spoken. When the server answers `nothing-new`, or that no agent is available, the layer says that one line itself; no turn runs. When the open fails, the line is `voiceAgentOpenFailureMessage`: the server's own reason when it gave one, that this connection is not allowed to use the agent, and otherwise that the server did not answer. What the user says goes to `voiceAgent.say` with `lampInterruptionContext`: what was said aloud in this answer (finished stretches plus the cut one's spoken part) and what was not (the cut one's rest plus everything not yet handed to the voice), or nothing when the agent had finished. From then on nothing more of the old answer is spoken (`lampSpeechDropped`): the server steers the running turn and the agent picks its point back up itself. When the user's words do not reach the agent (the call fails), the server steered nothing and the agent goes on with its answer, so the voice goes on with it: `lampSpokenOver` gives back exactly what that say took (the messages it silenced, what had been said, and the words the user cut off, which are said first), and one line says the agent did not get that. Keeping the voice quiet until the user says it again was the other choice; it leaves a voice layer silent with only that line to explain it, and the rest of the answer unheard if they do not. Said again before the voice has gone on, the agent is told the same interruption. A press of Space that is cancelled without words loses the rest of the stretch that was cut. The status line reads Listening, then Speaking, then Thinking (the conversation is opening, a message is being sent, the voice thread has a run under way, or the voice is making the first audio of a text), then Idle. While it reads Thinking, `LampIcon` in the button and the header gets `thinking`, which it passes on as `state="thinking"`. `useLampVoice` shares the status with the button through `lampVoice.state.ts`. **Screenshots:** `LampMediaPlayer` shows the one image the server says is in front of the user (`voiceAgent.subscribe`), read through the board's `agentsBoardMedia` RPC in the chat's project (`lampChatProjectId`: the thread's, or the draft's for a new chat with no thread yet), with the agent and time under it; the arrows call `voiceAgent.mediaStep`, so the agent's "next" continues from the user's click, and the image opens upstream's `ExpandedImageDialog`. **Transcript card:** each closed conversation the server lists for the chat is a card in the timeline at the time it happened. `useLampTranscriptRows` merges them into the timeline's rows after `useStableRows` as a fork row kind, `lamp-transcripts` (`withLampTranscriptRows` in `lampTranscript.logic.ts`): a card goes right before the first row created after the conversation opened, or at the end when no row is newer; rows without a time (worktree setup, sometimes the working row) never bound a card, and conversations in the same gap share one row. A conversation held during a folded turn sits right after the fold, before the first row the fold leaves showing, usually the turn's answer; opening the fold moves it to its exact place. The rows come back unchanged when there are no conversations, and a card row keeps its identity while its conversations stay the same, so the list's rows are not rebuilt for it. Every other reader of the rows (the minimap, the thread view, find, citations, position restore) looks for its own kinds and passes the new one by. The cards are client rows and not turn items because a turn item needs a run, which costs a paid turn. A chat with no messages draws no list, so there the cards are drawn at the top of the timeline (`empty`); a chat that has a list but no rows yet (only pending approvals or a history control) shows no cards until its first row; that includes a new chat with no thread yet, whose conversations the server keeps under the id the chat gets, so the card is still there after the first message. A click opens `LampTranscriptView`: the conversation on the thread view's glass, the user's turns on the right and the agent's on the left, read once with `voiceAgent.transcript`; Escape or a click outside closes it. It covers the chat the way the layer does, with the same `coverLampChat`. It suspends the thread view like the layer does, and the layer, find and the transcript close each other.

- **Why:** the voice agent has to stream, be steered while it answers, survive a reload and show on every client, and a thread already does all of that. So the agent is a thread: a hidden one under the chat the layer was opened over, on the Claude provider with the user's own sign-in, and its messages are the transcript. **The thread.** A delegated ("app-owned") child was the first idea and does not fit: `delegated_task.request` needs a run of the parent that is under way, and its result wakes the parent's agent, which is a paid turn nobody asked for. A side chat fork does not fit either: it copies the chat's provider, model and runtime mode and hands the chat's context to the first turn. So `VoiceAgent.open` dispatches an ordinary `thread.create` with `voiceAgentOf`, and the orchestrator stamps the lineage `{ parentThreadId, relationshipToParent: "fork", sideChat: true, voiceAgent: true }` with no context transfer. `sideChat` is what every server list, search, notification and the mobile app already leave out; `voiceAgent` is what the lock, the memory block and the MCP gate read, on the thread itself, so none of them depends on a file that can be lost. **Hidden on the client.** A side chat still shows in its chat: as a chip in the thread relationships control, which opens it in the right panel with a prompt box, and in the counts and requests that roll up to its chat. The voice thread must show in none of them: the chat gets a transcript card after the layer closes, and nothing else. So `environmentThreadsAtom`, the one list every thread shell atom of the client is derived from (the index a shell is looked up in, side chats by parent, child requests, the relationship shells, navigation), drops shells whose lineage says `voiceAgent`. The layer and the transcript do not need the shell: they read the thread by id, with the thread detail subscription and `voiceAgent.transcript`. A side chat tab left open on the voice thread by an earlier build reads "This side chat was deleted." and can be closed. An official client, which does not have the filter, shows the thread as a side chat named "Voice agent"; hiding it there would need the server's shell stream to leave it out, which is five places in upstream files against one here. Deleting the chat does not delete the voice thread (upstream finds a chat's side chats by their context transfer); it only stays hidden. One thread serves a chat for good and is reused on every open. **A new chat.** A chat with no messages has no thread on the server until its first message, and making one would be upstream's draft promotion done early. So `voiceAgent.open` takes the chat's `projectId` beside its thread id, and reads it only when the thread does not exist: the voice thread is made in that project, at the project's root, with `voiceAgentOf` set to the id the chat will get, and the conversation is recorded under that id. Nothing is created or sent in the chat itself, so no turn starts there. The card shows in the new chat as soon as the layer closes and stays when the chat gets its thread, because a draft keeps its thread id when it is sent; the one exception is a first send that fails after its thread was deleted, which gets a new id and loses the cards. Without a `projectId`, an unknown thread is still `thread-not-found`. **Model.** `VOICE_AGENT_DEFAULT_MODEL` in `packages/contracts/src/voiceAgent.ts` is the one setting: `claude-haiku-5-5`. A thread made for another value follows the constant from its next message. The provider is the usable Claude instance, the default one first (`lockedAgentProvider`); without one, `open` answers `unavailable` with one line that says what is missing (no Claude provider ready on the server, or Claude turned off for the project) and makes nothing. Other providers are not supported, because the lock below is written for Claude's query options only. The one exception is for trying the layer without a paid turn: a server run from source (`vp run dev`) with `T3CODE_VOICE_AGENT_REPLAY=1` in its environment runs the voice thread on the free `Replay (dev)` provider's `multi-turn` recording, two short answers of plain text with no model and no tool behind them, and always plays one when the layer opens. A packaged server has no Replay provider and ignores the variable. A chat's voice thread is reused only on the provider it was made for, so a thread never moves between Claude and the recording. **Updates.** On open the server refreshes the board (falling back to the last fetch after 8 seconds) and builds the changes since the cursor with `voiceAgentDigest`. The cursor is the set of message ids the board held at the last update, not a time, because the times on reports are the agents' own. It is kept by catalog project key in `<state dir>/voice-agent/state.json` and moves only when a conversation that was sent an update closes with something the agent said, so an update nobody heard is given again. With nothing new, no message is sent and no turn runs: the layer says the one line. Otherwise the thread gets `voiceAgentOpenedMessage` with the digest. What the user says arrives as `voiceAgentSaidMessage`, with the interruption when there is one, through `sendToThread` in `auto` mode, which steers a turn that is running and starts one otherwise. Both envelopes start with a tag, never a slash, and strip their own tags from what they quote. **Who the user is.** A report's `needs` line is often addressed to a person by name, and the agent can only tell "waiting for you" from "waiting for Sam" if it knows the user's name. `open` reads it once for each conversation from `AgentsBoard.signerName`, the same GitHub CLI lookup that signs the user's inbox messages, so the name is the one the other agents see; it is kept on the conversation and put on both envelopes as `user="Robin"`, on `<user_said>` too because an open with nothing new sends no opened message. The lookup shares the board refresh's 8 seconds. With no name (the GitHub CLI is not signed in) the envelopes carry no attribute, and the instructions read that as a user whose name is not known: a need that names nobody is theirs, and one that names a person is that person's. The name is cut to letters, digits and a few marks, so it cannot close the tag. The user's own messages to agents are left out of the next digest. **Conversations.** A conversation is the thread's messages between an open and a close, recorded in the state file. `close` stops a run that is still under way, counts the turns (`voiceAgentTurns`: the user's words out of their envelope, the agent's consecutive messages as one turn, the layer-opened message as none) and keeps the conversation only if there are any; `changes` lists only closed ones, which is why the card appears after the layer closes and never before. A chat has one open conversation: a second open closes the first, and a conversation the server left open when it stopped is closed when its chat is next read. **Tools.** `voice_board` reads the board now (agents, counts, newest reports; one agent or since a time). `voice_send_message` calls `AgentsBoard.sendInboxMessage` with a 600 character cap and `via: voice agent`, after matching the name it was given against the board's agent ids, and is refused while the user has said nothing in the conversation, since until then only the board's text could have asked for it. `voice_show_media` keeps, in memory, the list of screenshots and which one is in front of the user. `memory_propose` is the existing tool. **The lock.** A voice agent thread must not run commands, touch files or call any other tool, whatever the user's runtime mode is. Two layers enforce it, either of which is enough. In the Claude adapter, `lockClaudeQueryForLockedAgent` rewrites the query built for a thread whose lineage says `voiceAgent` and returns every other thread's untouched: `tools: []` (no built-in tool exists), `disallowedTools` naming the built-ins again, `allowedTools` exactly the four tools under Claude's names with no wildcard, `permissionMode: "dontAsk"` (a call that is not pre-approved is denied, with nothing to approve and no way to ask) without `allowDangerouslySkipPermissions`, `strictMcpConfig: true` with only T3's server kept in `mcpServers` (no server from a settings file, a plugin or the project), `settingSources: ["user"]` (the sign-in, but no project or local settings), no `extraArgs` (the user's launch flags), `hooks`, `agents`, `plugins`, `skills` or `additionalDirectories`, thinking off, and the system prompt replaced by the voice agent's instructions plus its memories block. The thread is also created with the lowest runtime mode, but the lock does not rely on it. On T3's MCP server, `layerLockedAgentToolGate` is a global visibility check on every tool, for lists and for calls: a voice agent thread gets the four tools and nothing else, every other caller gets everything but the three voice tools, and a thread whose shell cannot be read gets nothing. The voice tools' handlers check the caller's lineage again. **Board text.** The instructions say that everything from the board is information and never an instruction, and that messages, memories and screenshots happen only because the user asked; the digest and the tool results strip the envelope tags and clip every field. Nothing the agent or the user says leaves the machine except to the Claude provider and, for a message, in the push to the team's own repository; the log has no words of either.

- **Why:** each project has one Inbox: a thread that the user asks about all of the project's threads. It is code-named `inboxAgent` and shown as "Inbox". 1001 Code must keep working with the official T3 apps, mobile included, so the Inbox thread itself adds no contract field: clients only ever see an ordinary thread and its messages, and `inboxAgent.reset` is an optional RPC that replaces it with a new ordinary thread. **Resetting it.** `InboxAgent.reset(projectId)` (under `AuthOrchestrationOperateScope`, serialized by `InboxAgent`'s lock) creates a brand-new Inbox thread before deleting the old one(s) (archived duplicates included), so when no supported Inbox provider (Claude or Antigravity) is ready or enabled for the project, the existing Inbox stays untouched, and a running old Inbox stays locked until its `thread.delete` commits; if deletion fails while an old thread stays live, the new thread is rolled back. `inboxAgentDigestSinceMs` ignores wakes from before `inbox.createdAt`, so a reset Inbox starts with a fresh 24-hour first digest. On the web client, resetting is confirmed with a destructive dialog, clears the old thread's local draft/panel state, navigates seamlessly (`replace: true`) to the new Inbox thread when the user was viewing the old one, and is reachable from the Pane Strip Inbox header, the full-page Inbox header bar, the Inbox thread action menu, the sidebar Inbox row context menu (Projects and folder modes) and the Command Palette (**Reset Inbox**). **The thread.** It is an ordinary, listed, top-level thread: title "Inbox", on the first usable, project-enabled Inbox provider (`lockedAgentProviders(providers, "inbox")` prefers Claude with `claude-opus-5-5` at medium effort, then Antigravity with `ANTIGRAVITY_DEFAULT_MODEL`; an Inbox made before keeps its model), `full-access` (upstream's `t3_thread_send` refuses a target in broader modes than the caller's, and most threads run at full access; the lock still gives it no shell or file tools; `ensure` raises an Inbox an older build made at `approval-required` with `thread.runtime-mode.set`, unless it is running, since the change ends its session; a refused raise only logs, and each try gets a new command id, because a refusal is recorded against its id), no branch or worktree (the project root), `createdBy: "system"`, `creationSource: "server"`, made with the ordinary `thread.create` and no message, so making it starts no paid turn. Official clients and mobile list it like any thread. **Which thread it is (server).** `<state dir>/inbox-agent/state.json` maps each project id to its Inbox thread id. `InboxAgent` loads it at startup into `inboxAgentThreads.ts`, a process-wide record that `isInboxThread(threadId)` answers from memory; it is process-wide because the orchestrator, the adapters and the checkpoint services are upstream code that cannot take a new service. Only `InboxAgent` writes it. **Making it.** Everything goes through `InboxAgent.ensure(projectId)`, under one semaphore: the recorded thread while it is not deleted, else the oldest thread of the project that `isInboxThreadShell` accepts (archived ones included; this is what clients pick, so a lost state file changes nothing), else a new one. The No project folder gets none. Without a usable Inbox provider (Claude or Antigravity), or with all of them off for the project, it makes nothing and marks itself waiting (`waiting-for-provider`). The triggers sit in one function (`watch`), so the rule for when an Inbox is made can change there alone: `ensureAll` once the server is active, `ensure` on every `project.created` application event, and `ensureAll` again on a provider or settings change while a project waits and a supported provider is now ready. A deleted Inbox is replaced on the next startup (or provider retry). Ids are the time and a counter, because a deleted thread's id stays taken. **Which thread it is (clients).** `isInboxThreadShell`: title exactly "Inbox", `createdBy: "system"`, `creationSource: "server"`, no parent. Clients cannot create a thread as the system (the WebSocket handler stamps `user`, MCP stamps `agent`), and the guard keeps the name, so the title plus the creation fields are enough; of several, the oldest wins, as on the server. An imported native session titled "Inbox" would also match; that is accepted. **The lock.** The voice agent's lock and gate are one shared module for every locked kind; `lockedAgentKindOf` reads the voice agent from its lineage and the Inbox from the record. `lockClaudeQueryForLockedAgent` applies each kind's profile on Claude: the tools of `LOCKED_AGENT_TOOL_NAMES[kind]` (the Inbox's are exactly `t3_thread_list`, `t3_thread_read`, `t3_thread_search`, `t3_thread_send`, `t3_thread_wait`, `t3_thread_launch`, `orchestrator_capabilities`, `board_list`, `memory_propose`, `memory_withdraw` and `inbox_forward`, which no other caller lists), the same closed doors as the voice agent (no built-ins, `dontAsk`, only T3's MCP server, user settings only, no hooks, agents, plugins, skills or directories), and its own system prompt plus the project memory block. The Inbox keeps the thread's thinking and the adapter's `thinking-display` flag, the one launch flag kept. On Antigravity, `lockedAgentAntigravityLock.ts` enforces the equivalent lock: `_meta.antigravity` sets `enabledTools: []` plus `disabledTools` naming Antigravity's built-ins, `eagerMcpServers: ["t3-code"]`, and `systemPrompt: { append: INBOX_AGENT_INSTRUCTIONS }`; client FS/terminal capabilities and `additionalDirectories` are off; only the `t3-code` MCP server stays; `T3_ACP_MCP_*` shell-fallback env vars are stripped; the runtime stays in `"default"` mode and refuses client file reads; `permissionDisposition` auto-allows only `LOCKED_AGENT_TOOL_NAMES[kind]` on `t3-code` and denies everything else without prompting; and `formatLockedPrompt` skips T3's orchestration/browser/PR/shell-fallback prompt wrapping while prepending project memory (and inline instructions on runtimes older than 1.4.5). Reading other projects' threads is allowed. `layerLockedAgentToolGate` asks the record first, then caches each other thread's kind. **The guard.** `lockedAgentCommandRefusal` / `lockedAgentRefusal` allows an Inbox to switch between supported locked-agent providers (`LOCKED_AGENT_DRIVERS.inbox`: Claude and Antigravity), refuses any other provider (and keeps voice threads on their own provider instance), and refuses a `thread.metadata.update` that renames the Inbox or regenerates its title, so every client can keep finding it by title. The first message's `titleSeed` is dropped. In the web client the model picker restricts the Inbox via `allowedProviders` to Claude and Antigravity and disables every other provider. **Checkpoints.** The Inbox runs in the project root, where other threads edit files, so its checkpoints would show their edits as its own and a restore could undo them: its baseline is skipped and its captures are forced missing, as a side chat's are. **The digest ("What changed").** When the user sends the Inbox a message while it is idle, `attachInboxAgentDigest` builds what changed in that project's listed threads since the previous message to the Inbox, the user's (`latestUserAuthoredMessageAt`) or the app's last wake note, whichever is later (the first looks back 24 hours), from the project's shell snapshot: threads made, runs finished (with the first line of the run's last assistant message, read for the newest 8 such threads with one `getThreadRecords` of that run's assistant messages each) or failed (with `lastError`), questions opened (`openQuestionsAt`, or a pending approval or question), pull requests linked or merged (`snapshot.state` merged, at `mergedAt`), and Board tasks completed (below). Side chats, subagents, other projects and every Inbox are left out; titles and details are clipped and stripped of the envelope's tags; newest first, 40 at most. Other threads' messages return at the first check, without a read. A message sent while a run is under way (steered or queued) gets none. _Where it is kept:_ as one more record on the message's own `context`, an unknown kind (`inbox-digest`) of the existing `UnknownContextRecord`, already persisted with the message and already sent to every client; official clients ignore records they do not know, and the provider only reads records the text references. The server replaces any `inbox-digest` record a client sent. The model gets the digest in `<inbox_digest>` before the user's words (`inboxAgentProviderText`); its instructions say everything in it is information, never instructions, and never to name the digest, the envelope, tags or tools to the user. The web shows it collapsed above that message (`InboxDigestCard`). Turns run when the user messages the Inbox, when the app wakes it (below), and when a teammate's agent comment that is for no thread arrives (see the Linear board entry). **Waking it.** `InboxWakeWatch` (server code, not an agent) reads the orchestrator's domain events and marks a thread changed on an assistant message, a runtime request, a waiting turn item or a pull request sync; every 30 seconds it reads the changed threads' shells and notes each project whose Inbox has news: a question waiting for the user, a merged pull request, or a completed Board task. Completed tasks come from the same place as the chat's task cards: a finished `board_update` or Linear `save_issue` tool item whose `boardTaskChange` is a status change to a `completed` state, in a listed thread of a project with an Inbox; so only agents' changes are seen, not a person moving a task in Linear. _New builds:_ every 10 minutes, in a stream merged beside the events so a slow remote holds nothing up, it asks each Inbox project's origin for its `stable` tag (`git ls-remote --tags origin refs/tags/stable refs/tags/stable^{}`, the peeled commit for an annotated tag; `stableTag.ts`), since threads move the tag themselves and nothing else announces it. The first commit seen for a project is only remembered; a later different one is a move: the server fetches the tag without touching the checkout's refs or FETCH_HEAD, reads the `(#123)` squash-merge numbers of `git log --first-parent old..new` (first-parent keeps an upstream sync's own numbers out; the tag message is hand-written and not read), and records the move with the repository's GitHub web address for links. Its wake line is "New build:", the short commit in a code span, then each pull request as a `[#104](<repo>/pull/104)` link with its title and "Run your update command to get it." (commit titles lose brackets, so they cannot add links; the build's own update command is named by no public text), and the digest gets a`stable-moved` entry on the Inbox's own thread. Version tags are not watched. Two minutes after a project's first news (`inboxWakeTiming`), and at least two minutes after its last wake, under 40 wakes a day, and only while the Inbox is idle (else the next tick tries again), it reads the project's shells, builds the events not yet reported since the later of the first start and the user's last typed message (24 hours at most; `inboxWakeEvents`, questions first), and dispatches one Inbox message: `createdBy: "agent"`, `creationSource: "server"` (as the usage-limit and delegated-task wakes stamp theirs; clients show it as from T3 Code, and `inboxSendRefusal` refuses `t3_thread_send` in its turn), no model selection (the thread's own), `queue_after_active`, text `[Inbox update] N changes in this project's threads:` then one `- Kind: [title](t3-thread://v2/<environment>/<thread>): detail` line per event (`formatThreadLink`, ten at most), and the digest record a user message gets (its window reaches back to the oldest event, so a merge synced after an earlier wake still shows). `<state dir>/inbox-agent/wake.json` (version 2; a version 1 file is read as empty, which only restarts the reporting window) keeps the reported event keys, each project's wake times, the completed tasks and stable moves (a week, for the digest and the moment cards), each project's last `stable` commit, so a restart neither repeats an event nor resets the cap; after a restart every Inbox project is checked once at the first due tick. The digest reads the tasks and the last wake time from a process-wide copy, as it reads the Linear inbox's log. The instructions' "Updates from the app" section tells the model what the marker means: one linked line per event, questions first, a next step or a card, and no send. **Where it opens (web).** Without project folders, a **Projects** section sits at the top of the thread list, below the drafts: one row per project in the project filter's scope (every pickable project when none is picked). With folders on (`boringSidebarEnabled`), each folder's first row is **Inbox**, hidden in a closed folder unless the Inbox is open. The normal thread list leaves Inbox threads out (`withoutInboxThreads`, in the sidebar only: `environmentThreadsAtom` keeps them, since `ChatView` resolves the route thread from it). Every row shows a dot while the Inbox runs or waits on the user, is highlighted when its Inbox is the route thread, and opens it at the ordinary thread route; the palette's **Open Inbox** does the same for the project on screen. A multi-selection's right-click menu starts with **Message from Inbox…**, which adds the selected threads to that Inbox's composer draft as thread-context chips through the draft store's `addThreadContexts` (the record a drag into the composer adds, so chips already there are kept once), opens the Inbox like the rows and focuses its composer; it is disabled with a hint when the selection spans projects or environments or the project has no Inbox yet, and an Inbox in the selection is never a chip. With no Inbox yet, the row and the action are disabled and say the server makes it once Claude or Antigravity is ready. In the Inbox, the composer reads "Ask about this project's threads", the thread details panel has no Version Control section (environment, Open in, usage and cost stay), and the title bar has no terminal toggle (the keybinding still opens one). **Messaging threads.** The Inbox sends with upstream's `t3_thread_send` and `t3_thread_wait`, and reads the answer with `t3_thread_read`. The gate refuses an Inbox's `t3_thread_send` call (`inboxSendRefusal`, a JSON-RPC error with the reason) unless the Inbox's active run answers the user's own typed message (the run's `userMessageId` has `createdBy: "user"` and no `senderThreadId`, `linkedSender`, `scheduledTaskId` or guest), and the target is another thread of the Inbox's project in this environment; anything it cannot read refuses. The check sits in the gate because the gate already runs for every call with the caller's thread and sees the call's arguments, so no upstream file changes; the tool stays listed, since tool lists are cached per session. Reads of other projects stay allowed. **Forwarding teammates' messages.** A teammate's message that reached the Inbox goes on with `inbox_forward` (`threadId`, `commentId`): `LinearInbox.forward` sends the Inbox's copy unchanged (same text, same `linkedSender`) to the target with `sendToThread` in `queue` mode, under the id a direct delivery would get, and logs it, so the target may answer with `board_reply`. The model picks only the target and sends no words of its own, so it may forward in any turn. The arguments take the comment id, which the model reads in the closing marker, because it never sees message ids. The gate refuses (`inboxForwardRefusal`, the same check the service runs) a comment the log does not show delivered to this Inbox, a message that lost its sender or framing, a target in another project or environment, the Inbox itself, and anything it cannot read. The Inbox's prompt replaces Claude Code's, so `INBOX_AGENT_INSTRUCTIONS` carries `QUESTION_CARD_INSTRUCTIONS` itself, for the pick-any card it shows before a send it chose by relevance, plus its own "Questions and next steps" section: the card shape with one right and one wrong example of the bare ` _(recommended)_` marker (the model had written `*(recommended: reason)*`, which does not render), and the rule to end a report with the next step or a card when the user must decide. **Starting threads.** The Inbox starts a thread with upstream's `t3_thread_launch`, and lists models with `orchestrator_capabilities` (a read of the providers and models, nothing else). The gate refuses an Inbox's launch (`inboxLaunchRefusal`, sharing the user-started check with sends) outside a run answering the user's own message, with `scratch`, `delegatedFrom`, another `projectId` or `environmentId`, or without a `worktree` `workspaceStrategy`: every Inbox launch gets its own worktree, since the project root is where other threads work. Upstream's launch hands a thread caller's model and mode down to the new thread, which for the Inbox would be its own model at full access; `launchInheritsFrom` makes an Inbox caller resolve an omitted model and mode from the project's defaults, as a caller outside a thread does and as the composer's New thread does, still under the Inbox's ceiling. A model or mode the Inbox passes is honored. Its instructions launch at once when the user asks, ask a yes/no card before a thread it only suggests, and, with no saved preference, ask one model question before its first launch and then propose the answer as a memory (its prompt carries the memory block). Adding the two tools changes what an Inbox may call, which is not backwards compatible; no stored data changes.
